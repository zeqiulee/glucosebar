# GlucoseBar 首次发布与首两周计划

这是一份维护者操作手册。仓库使用 `zeqiulee/glucosebar`；版本实际公开前，不要把预定下载链接写成“现已上线”。更新于 2026-10-26。

## 先让对的人成功用起来

第一批用户应同时满足：使用 macOS 14 或更新系统、佩戴国内版硅基动感 GS1、通过 iPhone 原 App 上传数据，并能接受测试版及手动获取本人登录凭证的步骤。先服务这类用户，不把宣传范围扩大到所有动态血糖仪用户。

产品的一句话介绍：**在 Mac 菜单栏查看硅基动感 GS1 已上传的血糖读数和趋势。** 这是独立辅助查看工具，不是厂商官方客户端。当前连接来自社区研究的云端接口，不能承诺厂商接口长期稳定；不宣传蓝牙直连、Apple 健康同步、即时告警或治疗效果。

当前公开分发仍有门槛：只有本机验证过的 App 不代表陌生 Mac 能直接安装。完成 Developer ID 签名、公证及另一台 Mac 的下载测试前，先发布源码与明确标识的技术预览，招募愿意自行构建的测试者。此时不要用“下载即用”招募普通用户。分发文件是否已签名公证，以每个 Release 的说明为准。[Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

## GitHub 上的几个入口分别做什么

| 入口 | 对用户的作用 | 维护者需要准备什么 |
| --- | --- | --- |
| 仓库首页 / README | 了解产品、支持范围和上手方式 | 一句话介绍、演示图、兼容列表、上手教程、当前限制 |
| Releases | 获取指定版本、安装包和版本说明 | 系统与芯片要求、签名公证状态、校验和、变更与已知问题 |
| Star | 收藏项目、表达兴趣 | 可以邀请感兴趣的人收藏，不把 Star 当作实际用户数 |
| Watch → Custom → Releases | 订阅新版本通知 | 告诉需要更新提醒的人如何订阅，而不是要求关注全部动态 |
| Issues | 报告软件问题、提出建议 | 隐私提醒、模板、明确可提供和禁止提供的信息 |
| Pull requests | 提交代码或文档修改 | 贡献指南、测试步骤、可认领的小任务 |

GitHub 的 `Code → Download ZIP` 和 Release 里的 `Source code` 都是源码，不等于可双击安装的 App。普通用户应进入 Release 的 Assets，按说明选择适合芯片的应用压缩包。源码可以先公开；Release 草稿还不是对外可见的正式下载页面。[GitHub Releases 说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

Star 与更新通知是两件事。[Star 说明](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars)、[Watch 通知设置](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications)

## 第一次公开前，按这个顺序完成

1. **确认名称、开源许可证和署名。** 许可证以最终 `LICENSE` 为准；没有许可证不能只凭“仓库公开”就承诺别人可任意修改分发。维护者确认后再发布。
2. **只上传产品目录。** 不上传钥匙串数据、本机血糖缓存、抓包文件、真实接口响应、个人截图、签名私钥或聊天记录。演示图统一使用合成数据并写“演示数据”。
3. **把首页写给新用户。** 第一屏说清“给谁用、能看到什么、目前怎么安装”；把开发细节放到后面。中文优先，保留简短英文简介便于搜索。
4. **设置仓库 About。** 可用描述：`macOS menu bar glucose viewer for China-region SiSensing GS1 cloud data.` 主题只用真实相关的词，例如 `macos`、`swiftui`、`menubar`、`cgm`、`sisensing`。不要堆与产品无关的热门词。
5. **跑测试并检查自动构建。** 主分支应能构建；版本号和发布标签一致；下载文件区分 Apple Silicon / Intel。能编译不等于已在两种机器上实测。
6. **先创建 Release 草稿。** 检查说明、包名、SHA-256、签名公证状态和兼容性。没有经过另一台 Mac 下载运行的版本，仍标为技术预览。
7. **走一遍全新用户流程。** 请一个没看过开发过程的人，只靠 README 完成操作。记录卡在哪一步，先修教程和错误提示，再邀请下一批。
8. **公开后核对链接。** 用未登录 GitHub 的窗口确认 README 和公开 Release 可见、图片加载、下载入口正确；不要把只有维护者能打开的草稿链接发出去。

公开文档的建议优先级：README → 安装/连接教程 → 已知限制 → 隐私说明 → Issue 模板 → 贡献指南。不要为了第一天“看起来成熟”写大量没人使用的功能承诺。

## 先找 10 名匹配用户，分 2 + 3 + 5 三批

这是验证用的小样本计划，不是增长承诺。先邀请你已经认识、愿意试用的匹配用户；不要向陌生人群发私信。无签名公证时，先找愿意从源码构建的技术用户，普通用户测试等可信分发通道准备好后再进行。

每位测试者自行在自己的设备输入凭证；你不接收、不代填、不远程索取凭证。可以指导步骤，不要求对方发送完整屏幕或抓包记录。

| 检查项 | 测试者做什么 | 只反馈什么 |
| --- | --- | --- |
| 新 Mac 安装 | 从公开说明中的入口取得对应版本，按教程启动 | 成功 / 卡在哪一步、App 版本、macOS 大版本、芯片类型 |
| 首次连接 | 按教程获取本人凭证，只粘进本机 App；自行与手机核对值和测量时间 | 一致 / 不一致、哪一步不清楚；不发送实际读数 |
| 两种菜单栏模式 | 切换曲线和数字，关闭面板后继续观察 | 是否看得清、切换是否立即生效 |
| 3 / 6 / 12 / 24 小时 | 切换范围，试悬停查看测量点和时间 | 排版或交互问题，不上传真实曲线 |
| 过期与断网 | 在方便时短暂断网，观察旧数据标记；联网后看是否恢复 | 是否明确标记旧数据、是否恢复；不以此测试原 App 的告警能力 |
| 失效与错误 | 自然遇到凭证失效时记录错误类别；合成错误场景由维护者测试 | 错误文案与恢复路径是否清楚；不为测试主动退出手机账号或停用传感器 |
| 退出与重新启动 | 在面板点击“退出”，再启动 | 菜单栏是否退出、设置是否保留、是否出现重复进程 |
| 停用与卸载 | 关闭登录启动、清除凭证与缓存；确认结果后退出并移除 App | 是否完成；若出现清除失败提示，只记录文字类别 |

出现错误账号数据、数据过期却无标识、凭证泄露、清除失败但提示成功等问题时，暂停扩大测试，先修复。不要收集对方的传感器序列号、手机号或健康史来排查普通软件问题。

第一批 2 人用于找出教程中最大的阻碍；修复后再做 3 人；流程稳定后再邀请 5 人。首批验收目标是“没有必须由维护者代操作的连接步骤、没有未解决的隐私和旧数据标识问题”，而不是凑够 10 次下载。

## 首两周怎么安排

时间从“存在可公开使用的测试版本”起算。未公证或首次连接流程仍频繁失败时，延后面向普通用户的宣传。

| 时间 | 具体行动 | 当天留下的结果 |
| --- | --- | --- |
| 第 1–2 天 | 完成首页、30 秒演示、版本说明；邀请第一批 2 人 | 一份卡点清单、真实支持范围、改好的教程 |
| 第 3–4 天 | 修复最常见卡点；第二批 3 人独立测试 | 一个修复版本，Release 写清修了什么 |
| 第 5–7 天 | 邀请第三批 5 人；在一个获准的目标用户社群分享一次 | 新的兼容性记录和经本人同意可引用的使用反馈 |
| 第 8–10 天 | 依据问题更新 FAQ；发布一次具体改进记录 | “问题 → 修复 → 如何升级”的短文，而不是重复首发广告 |
| 第 11–14 天 | 检查安装和连接反馈，联系愿意回访的测试者；决定是否扩大范围 | 两周复盘：继续、修复后再发，或暂缓推广 |

渠道顺序建议：

1. **已有的相关用户关系和社群。** 先读群规，向管理员说明独立工具、支持范围、测试状态；得到允许后发一次简短邀请。不要暗示厂商背书，不私自转贴群友健康数据。
2. **你自己的公开账号。** 用演示数据录屏，介绍自己为什么需要它，以及尚未解决的连接门槛；链接到 README 和对应 Release。先提供可用信息，再邀请反馈。
3. **开发者社区。** 可考虑 V2EX“分享创造”，但需由你本人按真实开发经历独立撰写。V2EX 当前规则明确不允许发布 AI 生成内容，不能把本目录里的 AI 文案直接粘过去，也不能换几个字后提交。发布前重新核对站点和节点规则。[V2EX 规则](https://v2ex.com/about)、[分享创造节点](https://www.v2ex.com/go/create)
4. **更广的产品发布渠道。** 等普通用户安装、连接和支持稳定后再考虑。当前支持的是中国区特定设备，广撒英文流量往往会吸引无法连接的用户；先补兼容性和英文教程，再决定是否需要国际发布。

不买 Star、不交换虚假下载、不刷榜、不在无关 Issue 下丢链接、不在多个群连续发同一广告。不要把教程包装成糖尿病诊断或治疗建议，也不把特定参考区间包装成所有人的健康标准。

## 不加埋点，也能知道产品有没有用

先用 GitHub 自带汇总信息和测试者自愿反馈。不要为推广新增血糖上传、设备指纹、后台追踪或第三方分析 SDK。

| 指标 | 怎么得到 | 能回答什么 / 不能回答什么 |
| --- | --- | --- |
| 仓库访问与来源 | 每周查看仓库 Insights → Traffic，人工记一次汇总 | 有人看过什么；不代表安装成功。GitHub 主要保留最近 14 天的访客等数据，图表使用 UTC 日期 |
| Release 文件下载次数 | 查看对应应用资产的 GitHub 汇总下载数 | 哪个包被下载；重复下载会计数，不是独立用户或活跃用户 |
| 尝试安装人数 | 测试者自愿勾选“已尝试安装” | 只代表参与反馈的样本，不外推全部下载者 |
| 安装 / 首次连接成功人数 | 测试者分别回报成功或所卡步骤 | 区分是安装门槛还是凭证流程问题 |
| 一周后仍在使用人数 | 只向同意回访的人询问一次 | 是否值得继续用；不是自动测得的 7 日留存率 |
| 未解决的重要问题 | Issue 分类和维护者清单 | 下一版该先修什么 |

GitHub 的访问统计与资产下载是不同维度，不要相除后声称得到准确转化率。[仓库流量说明](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository)、[Release 下载统计说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

## 日常维护：少承诺，及时回应

- 在你能承担的时间内固定检查 Issue，例如每周两次；只有确实能做到时才公开承诺响应时限。
- 把问题分成“安装”“连接”“界面”“兼容性”，先处理阻止使用或可能误导数据状态的问题。
- 收到重复问题，先修教程或错误提示，再给 Issue 指向该说明；不要反复让用户走同一套抓包流程。
- 每个 Release 说明改进、升级方法和仍存在的限制；不要只写“优化体验”。
- 对外引用反馈、截图或评价前，另行征得本人同意。即使同意，也优先用演示图，避免公开健康数据。
- 当接口变化导致不可用时，在首页和 Release 及时说明；不能保证维护时长时，如实写“个人维护的开源项目”。

更多关注通常来自四件可验证的事：定位准确、装得上、教程能跟完、遇到问题有人认真维护。先把这四件事做到，再扩大宣传范围。
